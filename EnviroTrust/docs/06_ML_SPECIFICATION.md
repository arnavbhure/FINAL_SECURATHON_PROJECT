# 06 — Machine Learning Specification

## 1. ML purpose

The ML component asks whether a cryptographically verified COD reading is consistent with the facility's separately signed simulated operating conditions and recent sensor history.

It does not verify signatures, authenticate devices, establish legal compliance or prove fraud.

## 2. Two detection capabilities

### Capability A — Process-context COD prediction (main ML model)

Train a `RandomForestRegressor` on synthetic normal operating data to predict outlet COD from signed operations-context features. Compare the predicted COD to the actual signed COD reading. A large residual creates a `PROCESS_CONTEXT_MISMATCH` alert.

### Capability B — Sensor behaviour rules (not a second ML model)

Use rolling-window rules for:

- Flatline / near-constant values.
- Sudden jumps/drops.
- Gradual drift if time permits.

The UI and report must call these rule/statistical detections, not a second trained AI model.

## 3. Data sources and trust requirements

### Pollution telemetry

COD reading from `COD-OUT-001`, signed with its own Ed25519 key, verified by primary before ML use.

### Operating context

Generated by a separate `OPS-001` simulator and signed with a different Ed25519 key. Fields:

- production rate
- wastewater flow
- treatment dosage
- energy consumption
- operating mode
- interval start/end

Primary verifies operations-context signature and maps it to the same site/station/time window.

Because the operations simulator and pollution simulators are all generated in one software prototype, they are logically separate synthetic sources, not genuinely independent physical evidence. The UI must state this.

## 4. Scope decision: COD only

In the 15-hour MVP, the regression model predicts COD only. pH and TSS are displayed and can use simple sensor-behaviour rules. Do not train separate models for pH/TSS during the first build.

## 5. Synthetic data generation

Generate approximately 1,500–3,000 normal synthetic rows with a fixed random seed. The generator must create variation across multiple operating modes and runs.

Suggested features:

| Feature | Type | Unit/meaning |
|---|---|---|
| `production_rate` | Numeric | simulated units/hour |
| `wastewater_flow` | Numeric | simulated L/hour |
| `treatment_dose` | Numeric | synthetic normalized dose units/hour |
| `energy_consumption` | Numeric | simulated kWh/hour |
| `operating_mode` | Categorical | `NORMAL`, `HIGH_LOAD`, `CLEANING`, `LOW_LOAD` |
| `outlet_cod` | Numeric target | mg/L |

Use a documented synthetic process generator with noise and operating-mode effects. The formula is a simulation assumption, not a validated industrial process model. It should produce plausible positive values and ensure that treatment/flow/mode have explainable effects. Do not hardcode the answer to the injected attack rows.

Training labels must be generated before attack injection. Attack samples belong in a separate test set and must not be included in normal training data.


### Reproducible synthetic generator (hackathon-only)

Use a fixed seed, e.g. `random_state=42`, and generate records in independent simulation runs. The generator is not a model of any named industry; it is a controllable synthetic process used to test whether the pipeline works.

A practical starting recipe:

1. Sample `production_rate` from a bounded positive range, e.g. 100–1000 synthetic units/hour.
2. Sample `wastewater_flow` from a positive range and add a documented relationship to production plus random variation.
3. Sample `treatment_dose` from a bounded range; vary it by operating mode.
4. Derive `energy_consumption` from production plus noise.
5. Assign an `operating_mode` (`NORMAL`, `HIGH_LOAD`, `CLEANING`, `LOW_LOAD`) and give each mode a documented effect in the generator.
6. Calculate a synthetic latent incoming-load term from production and flow.
7. Calculate a synthetic treatment-efficiency term from treatment dose and operating mode, clipped to a safe interval.
8. Calculate `outlet_cod = latent_load * (1 - treatment_efficiency) + measurement_noise`, clipped to a positive configured range.
9. Save generator parameters and seed in `models/metadata.json`.

The exact coefficients are simulation parameters. Put them in one `SyntheticProcessConfig` rather than scattering constants. Document that these coefficients are invented for a controlled demo and have no regulatory/scientific authority. Ensure the generated dataset has enough overlapping feature combinations so the model is not simply learning operating-mode labels.

### Attack injection

Create attack cases only after splitting the normal data:

- `CONTEXT_MISMATCH_DROP`: keep the operating context but replace outlet COD with a deliberately low value relative to generated normal process behaviour.
- `FLATLINE`: repeat a nearly identical COD value over at least the configured window; preserve valid signatures in the sensor simulator.
- `SUDDEN_CHANGE`: introduce an abrupt step in COD not explained by context.
- `NORMAL_TRANSITION`: legitimate switch between operating modes; use this to test false positives.

The model must be trained only on normal rows. Evaluate injected cases separately. Include normal transition cases because they help expose a naive detector that flags every sudden change.

## 6. Recommended model

Use `sklearn.ensemble.RandomForestRegressor` with a simple, reproducible configuration, e.g.:

- `n_estimators=100`
- `min_samples_leaf=2`
- `random_state=42`
- `n_jobs=-1`

These are starting values, not guaranteed optimal hyperparameters. Keep them in a config file. Encode categorical `operating_mode` through a `ColumnTransformer`/`OneHotEncoder` pipeline or an equivalent stable preprocessing pipeline. Persist the entire fitted pipeline with `joblib`, not just the estimator.

Do not expose arbitrary pickle/joblib model uploads through the web API. Load only the model artifact packaged by the development team.

## 7. Training and evaluation procedure

1. Generate synthetic normal dataset with a fixed seed.
2. Sort/group by simulation run or time; avoid random row leakage from adjacent samples.
3. Split by run/time into train, validation and test (illustrative 70/15/15 split).
4. Fit preprocessing and RandomForestRegressor on training data only.
5. Use validation data to calculate absolute residuals.
6. Choose a configurable threshold using a percentile of normal validation residuals, e.g. the 99th percentile, then inspect false positives. Do not hardcode an arbitrary residual threshold.
7. Evaluate on untouched normal test data and separate injected anomaly scenarios.
8. Report MAE/RMSE for regression and precision/recall/F1 for labelled injected anomaly detection where appropriate.
9. Save model version, training seed, features and threshold with the artifact metadata.

Metrics on synthetic data only demonstrate behaviour on the synthetic generator. They do not prove field accuracy.

## 8. Runtime inference

For each COD reading:

1. Ensure COD signature and sequence checks passed.
2. Find a verified operations-context record that overlaps the COD measurement time according to a documented tolerance.
3. Reject stale/missing context for inference; return `NOT_EVALUATED`.
4. Convert inputs using the exact training feature pipeline.
5. Predict expected COD.
6. Compute `absoluteResidual = abs(actualCod - predictedCod)`.
7. Compare residual against saved validation-derived threshold.
8. Return `CONSISTENT` or `SUSPICIOUS` with reason and model version.

Do not use an old context record indefinitely. Do not mix site/station IDs. Do not infer missing features silently.

## 9. Sensor-behaviour rules

### Flatline

Use a rolling window (default 8 readings) and a configurable tolerance per parameter. Alert if the range of values in the window is below/equal to tolerance for the required consecutive windows. Account for measurement resolution and natural variation.

### Sudden change

Use a rolling median and median absolute deviation (MAD), or a documented z-score fallback. The rule must have a minimum history requirement and parameter-specific tuning. Treat as suspicious sensor behaviour, not proof of fraud.

### Drift (P1)

Compare the rolling median/mean of current window to a baseline window and alert if deviation persists over configured windows. Avoid alerting on legitimate mode transitions without context.

## 10. API contract

Endpoint: `POST /ml/v1/analyze/cod`. The exact request body is `contracts/ml-request.schema.json`; the exact response body is `contracts/ml-result.schema.json`. Do not create a second, incompatible shape.

Request contains:

- `readingId`, `siteId`, `stationId`, `sensorId`
- `actualCod`, `measuredAt`
- `context` object with the exact signed and verified operations-context features above
- `recentCodReadings` array for behaviour rules
- `contextVerified: true` set internally by primary only after OPS-001 signature, site/station mapping, freshness and interval-alignment checks. Never accept this flag from browser input.

### Service authentication and network boundary

- The ML service is private/internal and must not be exposed directly to browsers or unauthenticated public users.
- Primary calls ML with `Authorization: Bearer <ML_SERVICE_TOKEN>` when configured. The ML service validates this token using constant-time comparison.
- `ML_SERVICE_TOKEN` must be configured separately in the primary API and ML service environment with the same random value. Never expose it in a `VITE_` variable or logs.
- Bind the local ML service to `127.0.0.1` for local development. For deployment, use private networking and HTTPS/service authentication.
- If service authentication is misconfigured, return an authorization error and mark analysis unavailable; do not bypass the auth check silently.

Response follows `contracts/ml-result.schema.json` and includes:

- `readingId`
- `status`: `CONSISTENT`, `SUSPICIOUS`, `NOT_EVALUATED`, `ERROR`
- `anomalyType`
- `actualCod`, `predictedCod`, `absoluteResidual`, `threshold`
- `modelVersion`
- `reasons` array
- `evaluatedAt`

Never return `fraudProbability` unless a calibrated probabilistic model is later developed and validated. Random forest regression residual is not a fraud probability.

## 11. Scenario tests

- Normal COD under normal context → usually consistent.
- High production/flow/treatment context with deliberately implausibly low COD according to synthetic generator → suspicious residual.
- Same context with expected COD → consistent.
- Missing context → not evaluated.
- Stale context → not evaluated.
- Flatline values with valid signatures → flatline rule alert.
- Sudden change → rule alert if threshold crossed.
- pH/TSS values outside demo compliance limit → compliance alert, not automatically ML fraud.

## 12. ML output interpretation

The alert means “this reading is inconsistent with the model's learned synthetic operating pattern.” It does not mean “the factory cheated.” An operator/auditor must investigate.
